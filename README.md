# Tadka (TypeScript edition)

This is the `ep02-typed-tool-calling` branch of [tadka-ai](https://github.com/desiarchitect/tadka-ai). The `main` branch explains how the episode branches fit together.

A small food-delivery backend used as the running project of an AI engineering series.
One TypeScript codebase: a modular monolith API plus a fake payment provider.

> Episode 2: typed tool calling with server-side identity. The model requests a tool, the executor validates the request, the service enforces access, and the application decides what can be claimed: replies are rendered from tool results, never written by the model. Episode 1's deterministic route and intent classifier are still here. Not included yet, on purpose: conversations, tools that change anything, RAG, prompt-injection defences.
> To run it, follow [RUNBOOK.md](RUNBOOK.md). To see what this branch added, read [CHANGELOG.md](CHANGELOG.md).

## What is here

| Path | What |
|---|---|
| `apps/api` | Fastify 5 + zod API. Modules: `identity`, `restaurants`, `orders`, `payments`, `assist` (intent classification, three read-only tools, executor, and agent loop behind `POST /assist/chat`, plus evaluator and triage) |
| `apps/api/demo` | A deliberately vulnerable naive tool, kept only to show the leak in a test. Never imported by the app |
| `apps/fake-psp` | Fake payment provider: charges, refunds, lookup by idempotency key, failure levers |
| `apps/web` | React 19 + Vite client: customer food-assistant view and developer diagnostics panel |
| `apps/api/migrations` | SQL generated by drizzle-kit. One Postgres, one schema per module, no cross-schema foreign keys |
| `docker-compose.yml` | Postgres 16 + pgvector; Jaeger under the `observability` profile |

## Requirements

- Node 24 or 26 (`.nvmrc` pins 24), pnpm 12.11.2, Docker with Compose.
- About 1 GB of free RAM for Postgres + Jaeger + Node processes; ~1 GB of disk for images.
- No paid credentials are needed for anything except the optional live LLM call.

## Run it

The full, explained version is in [RUNBOOK.md](RUNBOOK.md). The short version:

```bash
git clone https://github.com/desiarchitect/tadka-ai.git && cd tadka-ai
git checkout ep02-typed-tool-calling
npm install -g pnpm@12.11.2
pnpm install --frozen-lockfile
cp .env.example .env
docker compose --profile observability up -d --wait
pnpm db:migrate && pnpm db:seed
pnpm dev                       # API on :3000, fake PSP on :4010, web on :5173
```

## The assistant in the browser

`POST /assist/triage` needs a real provider (see below) or `DEMO_MODE=1` in `.env`. With neither it answers `503 provider_not_configured`.
In demo mode every answer says `simulated: true` and the page shows a SIMULATED badge. Only customers may call it, at most
`TRIAGE_RATE_LIMIT_PER_MIN` (10) times a minute per user. That limit is not a spending cap, and the `M0_BUDGET_USD` ledger covers only the CLI probe.
`pnpm dev` turns on the client's demo sign-in; a production build has it off. Details: RUNBOOK section 9.

## Episode 1: classify free text

```bash
pnpm eval:intent              # dry run: rules vs a stand-in model on 40 frozen messages, no key, no cost
pnpm eval:intent -- --live    # the same set against the model LLM_PROVIDER names, under a spending cap
```

Routes: `GET /assist/order-status?orderId=...` answers with no LLM. `POST /assist/intent` takes `{ "text": "..." }`, returns one of five labels
and a next step chosen by application code. It uses the keyword rules unless a model provider is configured (`LLM_PROVIDER` and its credentials, RUNBOOK section 11). Nothing cancels or refunds anything.

## Episode 2: ask with tools

```bash
pnpm --filter @tadka/api exec vitest run test/naive-tool-demo.test.ts   # the naive tool leaks; the real one does not
```

`POST /assist/chat` takes `{ "text": "..." }` from a logged-in customer and returns `{ answer, stopReason, steps }`. The model can call
`get_my_orders`, `get_order` and `get_restaurant_menu`; identity always comes from the token. Each question is limited to 6 model requests,
8 tool calls, 20 seconds, 32 KB per request and `ASSIST_TURN_BUDGET_USD`. It needs a configured model provider (`LLM_PROVIDER` and its credentials); without one
it returns 503. See RUNBOOK section 7.

## The LLM probe

```bash
pnpm probe:llm             # dry run with a fake model: no key, no network, no cost
pnpm probe:llm -- --live   # ONE real call to gpt-5.4-mini on the provider LLM_PROVIDER names
```

The model comes from `apps/api/src/llm`: `LLM_PROVIDER=azure` (Microsoft Foundry) or `LLM_PROVIDER=openai` (direct API); see RUNBOOK section 11.
For Foundry the live call needs `AZURE_RESOURCE_NAME` and `AZURE_API_KEY` in `.env`, and a deployment
of gpt-5.4-mini named like the model (`gpt-5.4-mini`, or set `AZURE_DEPLOYMENT`). It sends one synthetic message,
caps output at 400 tokens, turns reasoning off (`reasoningEffort: 'none'`), sets `maxRetries: 0`,
and asks the Responses API not to store the response (`store: false`).
Before sending, it checks a local ledger (`.m0-usage.json`) and refuses if the worst-case cost
would push total spend past `M0_BUDGET_USD` (default 5). Also set an Azure budget alert on the
resource group: an alert only notifies; the ledger is what stops the call.

## Costs

Everything runs locally for free. The only paid step is the optional live LLM call: at
gpt-5.4-mini's Global Standard price of $0.75 / $4.50 per 1M input / output tokens, one probe call
costs about a tenth of a cent at most. One assistant question is a few model requests, capped by `ASSIST_TURN_BUDGET_USD` (default $0.05).
